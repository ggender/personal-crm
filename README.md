# Личная CRM

Список людей, которых я знаю лично: кто это, откуда знакомы, телефон и почта, заметки о том, о чём договорились.

Что умеет:

- войти по ссылке из письма: на странице входа вводите почту, и на неё приходит письмо со ссылкой. Пароля нет, первый вход и есть регистрация. Ссылка работает один раз и 15 минут, новая ссылка отменяет прежние. На одну почту уходит не больше 3 писем за 10 минут. Вход держится 30 дней с последнего захода на этом устройстве, с нескольких устройств можно сидеть сразу. В шапке видны ваша почта и кнопка «Выйти» (она завершает вход только на этом устройстве). Без входа приложение не открывается, кроме проверки `/health`;
- вести свои контакты: каждый видит и меняет только свои контакты, заметки и группы. Чужой контакт по прямой ссылке не открывается («Контакт не найден»), у двух людей могут быть группы с одним названием, например «Друзья». Новый пользователь начинает с пустого списка. Контакты, которые были в базе до появления входа, и тестовые данные `pnpm db:seed` принадлежат пользователю с почтой из `OWNER_EMAIL`;
- открыть список всех своих контактов (по алфавиту, с разбивкой по буквам);
- найти человека по имени: регистр и «е/ё» не важны, слова можно писать в любом порядке («петров иван»);
- добавить контакт, в том числе сразу с первой заметкой «О чём договорились»;
- открыть карточку и дописать заметку после разговора: заметки идут от новых к старым, у каждой есть дата;
- изменить контакт (кнопка «Изменить» рядом с именем) или удалить его вместе с заметками (внизу страницы правки, после подтверждения);
- исправить отдельную заметку (значок карандаша у заметки);
- задать на странице контакта, как часто с ним общаться: раз в неделю, месяц, квартал или год. Выбор сохраняется сразу. Под переключателем видно «Связаться не позже 14 октября» или «Пора связаться: просрочено на 12 дней»;
- видеть на главной блок «Пора связаться»: все, с кем не общался дольше выбранного срока, сверху самые просроченные. Во время поиска блок скрыт;
- отметить «Пообщались» — в строке блока или на странице контакта — без заметки. Несколько секунд после нажатия можно нажать «Отменить». Общением считается новая заметка или «Пообщались», смотря что позже; если нет ни того, ни другого — дата добавления контакта. Дни считаются по московскому времени.
- разложить людей по группам («Семья», «Друзья», «Теннис» — любые свои). Группы отмечаются на странице контакта в строке «Группы»: нажал — человек в группе, нажал ещё раз — вышел; сохраняется сразу. Там же кнопкой «Новая группа» можно завести группу, и человек сразу в неё попадёт. Один человек может быть в нескольких группах;
- открыть страницу «Группы» (ссылка «Группы» рядом с фильтром на главной или «Настроить группы» на странице контакта): создать группу, переименовать, удалить. Названия до 50 символов, без повторов (большие и маленькие буквы не различаются). Если удалить группу, люди остаются в контактах — пропадает только группа. Нажатие на название группы открывает её людей;
- фильтровать главную по группе: под поиском ряд «Все», группы, «Без группы» (пока групп нет, ряда нет). Выбранная группа видна в адресе страницы, поэтому сохраняется после обновления и в ссылке. Поиск по имени работает внутри выбранной группы; если там никого не нашлось, есть ссылка «Искать во всех контактах». В списке под именем видны метки групп человека. Блок «Пора связаться» фильтр не учитывает: в нём все просроченные.

Данные хранятся в базе PostgreSQL, а не в браузере. Поэтому в другом браузере по тому же адресу после входа под той же почтой видны те же контакты.

### Как войти на компьютере

На компьютере письма никуда не уходят: их ловит Mailpit, почтовая заглушка из `docker-compose.yml`. Войти можно под любым адресом, даже выдуманным:

1. Откройте http://localhost:3000, введите почту (например, `test@example.com`) и нажмите «Получить ссылку».
2. Откройте http://localhost:8025 — там лежит письмо «Вход в Личную CRM». Нажмите в нём «Войти».

Письма в Mailpit хранятся в памяти и пропадают, когда `pnpm db:down` или перезапуск Docker останавливает его. Если Mailpit остановлен, приложение ответит «Не удалось отправить письмо. Попробуйте ещё раз.»; `pnpm db:up` запустит его снова.

## Что нужно на компьютере

- Node.js 24 и pnpm
- Docker Desktop (в нём работает база данных)
- OpenSpec — для работы над новыми фичами: `npm install -g @fission-ai/openspec@latest`

## Первый запуск

```bash
pnpm install        # поставить зависимости
pnpm env:init       # создать файл .env со случайными паролем и секретом (на экран они не выводятся)
```

Откройте `.env` и впишите свою почту после `OWNER_EMAIL=`: контакты, которые уже есть в базе, и тестовые данные достанутся пользователю с этой почтой.

```bash
pnpm db:setup       # поднять базу и Mailpit в Docker, создать таблицы и заполнить 1000 тестовых контактов
pnpm dev            # запустить приложение
```

Приложение откроется по адресу http://localhost:3000. Именно по этому адресу, а не по `127.0.0.1`: на него настроены ссылки для входа.

Если `.env` уже был от прошлой версии, `pnpm env:init` допишет в него только недостающие строки (секрет входа, адрес приложения, почтовую заглушку, `OWNER_EMAIL`) и ничего не изменит в остальных; после него впишите свою почту в `OWNER_EMAIL`.

## Обычный запуск

1. Запустите Docker Desktop.
2. `pnpm db:up` — поднять базу и Mailpit (если они уже работают, команда ничего не сломает). Письма со ссылками для входа видны на странице Mailpit: http://localhost:8025.
3. `pnpm dev` — запустить приложение. Остановить: `Ctrl+C` в терминале.

## Автотесты

Проверяют работу приложения на настоящей базе PostgreSQL.

1. Запустите Docker Desktop и базу: `pnpm db:up`.
2. `pnpm test` — прогнать все тесты один раз. `pnpm test:watch` — держать их запущенными и перезапускать при правках.

Тесты работают в отдельной базе `crm_test` в том же Docker: при первом запуске она создаётся сама. Рабочая база `crm` и ваши контакты в ней не затрагиваются; тесты отказываются работать с любой базой, имя которой не кончается на `_test`.

### e2e-тесты в браузере

Проходят сценарии так, как это делает человек: главный (войти → открыть список → добавить контакт → найти по имени → дописать заметку → обновить страницу и открыть тот же адрес «в другом браузере» — отдельный профиль без общих cookies — войдя под той же почтой: контакты и заметка на месте), «Не терять связь», группы, вход по ссылке из письма и «только своё» для двух пользователей в двух браузерах. Письма тесты читают из Mailpit, срок ссылок и входа проверяют, сдвигая даты в базе, а не дожидаясь.

1. Один раз на компьютере: `pnpm exec playwright install chromium` — скачать браузер для тестов.
2. Запустите Docker Desktop, базу и Mailpit: `pnpm db:up`.
3. `pnpm test:e2e` — тесты сами собирают приложение и запускают его на http://127.0.0.1:3100, это 15–30 секунд.

Свои данные у e2e-тестов — база `crm_e2e_test`, сборка — в папке `.next/e2e`. Поэтому они не мешают запущенному `pnpm dev`, обычным автотестам и вашим контактам. Если тест упал, снимок экрана и запись шагов лежат в `test-results/`; запись открывается командой `pnpm exec playwright show-trace <путь к trace.zip>`.

## Как устроено

- Next.js (App Router) + TypeScript, интерфейс на React, Tailwind CSS и shadcn/ui.
- База — PostgreSQL 18 в Docker, доступна только с этого компьютера (порт 5433).
- Структура базы описана в `src/db/schema.ts`, миграции лежат в `drizzle/`.
- Вход по ссылке из письма — Better Auth (`src/lib/auth.ts`), письма отправляет Nodemailer (`src/lib/mail.ts`): на компьютере в Mailpit, на сервере через Resend. Кто вошёл, определяет `src/lib/current-user.ts`; каждая функция работы с данными принимает пользователя первым параметром и видит только его записи.
- Браузер к базе не обращается: все запросы делает сервер Next.js (`src/lib/contacts.ts`, `src/app/actions.ts`).
- На компьютере приложение слушает только `localhost`, из сети его не видно. На сервере его видно через nginx: прод открыт всем, тест-стенд закрыт паролем (см. ниже).
- Требования к фичам ведутся в OpenSpec, папка `openspec/`: `specs/` — как работает то, что уже сделано, `changes/` — фичи в работе, `config.yaml` — что OpenSpec знает о проекте. Тексты требований — на русском. В Claude Code: `/opsx:propose` — описать фичу, `/opsx:apply` — сделать, `/opsx:archive` — закрыть готовую.

## Выкатка на сервер

На сервере два окружения. Сборка приложения в них одна и та же, но база, ключи и адрес у каждого свои:

|                  | Прод                                                         | Тест-стенд                                 |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------ |
| Адрес            | https://app.vprodcrm.ru                                      | https://test-app.vprodcrm.ru — под паролем |
| Новая версия     | только кнопкой **Deploy prod** и только прошедшая тест-стенд | сама, после каждого влития в `main`        |
| Данные           | настоящие                                                    | копия базы прода из бэкапа                 |
| Папка на сервере | `/srv/personal-crm`                                          | `/srv/personal-crm-staging`                |
| Бэкапы           | перед каждой выкаткой и каждый день в 03:00                  | нет                                        |

Проверка, что окружение живо и какая версия выкачена: `/health` на его адресе. Ответ — `{"status":"ok","version":"<коммит>"}`.

Без входа там ничего не видно, кроме `/health`: приложение открывается по ссылке из письма (см. «Что умеет»). Письма с настоящими ссылками на сервере уходят через Resend, домен `mail.crm.vprodcrm.ru`. Ссылка в письме ведёт на адрес того окружения, где запросили вход. Входы на стенде и на проде раздельные: кука входа живёт только на своём поддомене.

### Как выкатить новую версию

Напрямую в `main` отправить нельзя — она защищена. Путь такой:

1. Изменения — в отдельной ветке, из неё открыть pull request (PR) в `main` и включить автовлитие: `gh pr merge --auto --squash`.
2. На каждый PR GitHub Actions запускает проверки (**Actions → CI**): lint, формат (`pnpm format:check`), типы, автотесты Vitest, e2e-тесты Playwright и сборку образа. Все зелёные — PR вливается в `main` сам. Хоть одна красная — PR не вливается, пока причину не исправят. Если `main` ушла вперёд, ветку PR нужно обновить (кнопка **Update branch** или `gh pr update-branch`) — проверки пройдут заново.
3. Влитие в `main` запускает выкатку на тест-стенд (**Actions → Deploy staging**). Дальше всё само, обычно около 5 минут:
   - GitHub Actions собирает образ приложения с тегом — номером коммита — и кладёт его в GitHub Container Registry (GHCR).
   - **deploy-staging** копирует всю папку `deploy/` в папку стенда на сервере и запускает там `deploy.sh staging <образ>`: скачать образ → применить миграции базы (разовый контейнер; упали — новая версия не запускается) → запустить новую версию → проверить `/health` (smoke).
   - Прод при этом не меняется.
4. Проверьте новую версию руками на стенде: https://test-app.vprodcrm.ru.
5. Выкатите её на прод — это делаете вы:
   1. GitHub → вкладка **Actions** → слева **Deploy prod** → справа кнопка **Run workflow**.
   2. Ветка — `main`, поле **Commit to deploy** оставьте пустым, галочку **Roll back** не ставьте.
   3. Нажмите зелёную **Run workflow**. Выкатка идёт обычно 2–4 минуты.

Что делает **Deploy prod**:

- берёт коммит последней зелёной выкатки на стенд (историю выкаток стенда хранит GitHub);
- копирует на сервер скрипты `deploy/` из этого же коммита — на прод едет ровно та пара «образ + скрипты выкатки», что прошла стенд;
- `deploy.sh prod <образ>`: бэкап базы (не получился — выкатка останавливается) → скачать образ → миграции → запустить новую версию → smoke `/health`;
- после удачной выкатки чистит старые образы: на сервере удаляет образы старше 2 недель, кроме текущей и предыдущей версии прода и текущей версии стенда; в GHCR оставляет 10 последних сборок.

Что выкатилось — на странице запуска, в блоке итогов (Summary): `Deployed to prod: <коммит>` и откуда он взят. Если выкатка упала — `Deploy to prod FAILED`. Проверка руками: https://app.vprodcrm.ru/health показывает этот коммит в `version`; потом войдите и посмотрите, что контакты на месте. Отметка GitHub в **Environments → production** показывает коммит `main`, с которого нажали кнопку, а не выкаченный — смотрите итоги запуска или `/health`.

Поле **Commit to deploy** — запасной путь: выкатить не последнюю, а определённую версию. Номер коммита можно короткий, 7 знаков (`56470aa`). Прод примет только коммит, выкатка которого на стенд была зелёной; иначе запуск остановится с ошибкой и ничего не поменяет. Если на проде уже эта версия, выкатка пройдёт ещё раз: снимет бэкап и перезапустит то же приложение.

Выкатки на одно окружение идут по одной: вторая ждёт первую — и в GitHub, и если запустить `deploy.sh` руками (тогда ждёт до 10 минут, потом выходит с ошибкой и ничего не меняет). Выкатки на стенд и на прод друг друга не ждут: если пойдут одновременно, просто будут медленнее.

### Как откатить прод

Та же кнопка: **Actions → Deploy prod → Run workflow**, поставьте галочку **Roll back**, поле коммита не важно — **Run workflow**.

- Откат возвращает версию, которая работала на проде до текущей. Её помнит сервер (`PREVIOUS_IMAGE` в `/srv/personal-crm/release.env`), её образ всегда лежит на сервере. Стенд при откате не проверяется.
- На сервер едут образ и скрипты выкатки той версии, на которую откатываемся. Шаги те же: бэкап → миграции → запуск → smoke.
- В итогах запуска: `Deployed to prod: <коммит> — rollback from <коммит, с которого откатились>`.
- Повторный откат вернёт версию, с которой откатились: две последние версии меняются местами. Исправили ошибку — выкатывайте обычным **Deploy prod** с пустым полем, когда исправление пройдёт стенд.
- Откат меняет только код: изменения базы, которые успела сделать новая версия, остаются. Вернуть базу, какой она была до выкатки, — см. «Восстановление базы из бэкапа».

Если GitHub недоступен, откатить можно руками на сервере:

```bash
ssh crm
sudo cat /srv/personal-crm/release.env       # PREVIOUS_IMAGE — предыдущий образ
sudo -u deploy /srv/personal-crm/deploy.sh prod <значение PREVIOUS_IMAGE>
```

Так откатывается только образ: скрипты на сервере остаются те, что привезла последняя выкатка.

### Что нужно на сервере для входа

В `.env` каждого окружения кроме пароля базы лежат три строки. Файлы: `/srv/personal-crm/.env` у прода и `/srv/personal-crm-staging/.env` у стенда. Права 600, создаются и правятся руками на сервере. Значения у стенда свои: свой пароль базы, свой секрет, свой ключ Resend. Без любой из строк выкатка остановится на первой же команде, ещё до бэкапа и миграций, и данные не пострадают. Образец с пояснениями — `deploy/.env.example`.

- `BETTER_AUTH_SECRET` — секрет, которым подписываются cookie входа. Его создаёт команда из `deploy/.env.example`, на экран она значение не выводит. Если секрет поменять, все выйдут из приложения.
- `SMTP_URL` — почтовый сервер для писем со ссылками: `smtps://resend:<ключ API>@smtp.resend.com:465`. Ключ API — в Resend: https://resend.com/api-keys, права «Sending access», у каждого окружения свой. Домен `mail.crm.vprodcrm.ru` в Resend должен быть в статусе «Verified» (записи DNS для него добавляются на reg.ru). Если хостер закрыл порт 465, замените его на 2465 в `SMTP_URL`.
- `OWNER_EMAIL` — ваша почта. Миграция отдаёт контакты и группы, которые уже есть в базе, пользователю с этой почтой; входите под ней, и они на месте. Опечатались — данные уйдут пользователю с чужим адресом, поэтому сверьте строку до выкатки. Нужна, пока в базе есть данные.

Адрес, порт и папка каждого окружения — не секреты, они прописаны в `deploy/environments.sh`. Отправитель писем (`MAIL_FROM`) — в `deploy/compose.yaml`.

После выкатки откройте https://app.vprodcrm.ru — должна открыться страница входа. Войдите по своей почте (письмо придёт в настоящий ящик), внутри все контакты. С другой почтой список пуст. «Выйти» возвращает на страницу входа. На стенде — то же самое по адресу https://test-app.vprodcrm.ru, после логина и пароля стенда.

### Тест-стенд

Весь стенд, включая `/health`, закрыт логином и паролем nginx. Задать или сменить их — командой на своём компьютере. `LOGIN` в ней замените на свой логин латиницей. Пароль команда спросит два раза, на экран он не выводится, в файл попадает только хеш. Файл перезаписывается целиком:

```bash
ssh -t crm 'u=LOGIN; f=/etc/nginx/test-app.vprodcrm.ru.htpasswd; h="$(openssl passwd -6)" && sudo install -m 640 -o root -g www-data /dev/null $f && printf "%s:%s\n" "$u" "$h" | sudo tee $f >/dev/null'
```

Данные стенда — копия базы прода из самого нового бэкапа (обычно ежедневного, то есть не старше суток). Испортились — пересоздать заново:

```bash
ssh crm
sudo -u deploy /srv/personal-crm-staging/restore.sh
```

Скрипт покажет, какой бэкап прода загрузит, и подождёт `yes`. Потом заменит базу стенда, применит к ней миграции версии стенда и запустит приложение. Прод он не трогает и копию базы стенда не снимает. Нужна копия свежее последнего бэкапа — сначала снимите бэкап прода (его данные это не меняет):

```bash
ssh crm
sudo systemctl start personal-crm-backup.service    # то же, что ежедневный бэкап, но сейчас
```

Письма со стенда настоящие, уходят через свой ключ Resend. Других внешних сервисов у приложения пока нет. Сертификат у стенда свой (`test-app.vprodcrm.ru`) и продлевается сам, как сертификат прода.

### Если выкатка упала

Сама она ничего не откатывает. Упала выкатка на стенд — прод не тронут: исправьте причину и влейте исправление, стенд выкатится снова. Упала выкатка на прод — в итогах запуска `Deploy to prod FAILED`; дальше либо откат (см. «Как откатить прод»), либо исправление через стенд и новый **Deploy prod**.

Посмотреть, что случилось (у стенда — те же команды в папке `/srv/personal-crm-staging`):

```bash
ssh crm
sudo -u deploy /srv/personal-crm/compose.sh ps                 # что запущено
sudo -u deploy /srv/personal-crm/compose.sh logs --tail 100 app # последние логи приложения
```

Если в **Deploy prod** покраснел только последний шаг, **Remove old images from GHCR**, — выкатка прошла (в итогах `Deployed to prod`), не удалось только почистить старые образы в GHCR. Обычная причина — у репозитория нет прав удалять версии пакета: GitHub → ваш профиль → **Packages** → `personal-crm` → **Package settings** → **Manage Actions access**: у репозитория `personal-crm` должна быть роль **Admin**.

### Ежедневный бэкап

Каждый день в 03:00 по Москве таймер сервера `personal-crm-backup.timer` снимает бэкап базы прода (`deploy/daily-backup.sh`). Если в это время сервер был выключен, бэкап снимется сразу после включения. Если идёт выкатка или восстановление, бэкап подождёт их до 30 минут. У стенда ежедневного бэкапа нет.

Проверить:

```bash
ssh crm
systemctl list-timers personal-crm-backup.timer      # когда следующий и когда был прошлый
sudo journalctl -u personal-crm-backup -n 20          # что написал последний бэкап
sudo ls -l /srv/personal-crm/backups                  # файлы с _daily в имени
```

Таймер ставится на сервер руками один раз, выкатка его не ставит (как настройки nginx). Повторить — если пропал таймер или поменялись файлы в `deploy/systemd/` (сначала выкатите их на прод, потом выполните команды):

```bash
ssh crm
sudo install -m 644 /srv/personal-crm/systemd/personal-crm-backup.service /srv/personal-crm/systemd/personal-crm-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now personal-crm-backup.timer
```

### Восстановление базы из бэкапа

Бэкапы прода лежат в `/srv/personal-crm/backups/`. Здесь — про прод; база стенда пересоздаётся из бэкапа прода, см. «Тест-стенд».

- Перед каждой выкаткой прода (и откатом) — бэкап базы. Хранятся 7 самых новых.
- Каждый день в 03:00 — ежедневный бэкап (см. «Ежедневный бэкап»). Хранятся 7 самых новых, то есть за неделю.
- Лишние удаляются сразу после нового бэкапа того же вида.
- Копии `_before-restore` и снятые руками с другой меткой автоматически не удаляются. Не нужны — удалите сами: `sudo -u deploy rm /srv/personal-crm/backups/<имя файла>`.

Имя файла: `crm_<дата>_<время>_<версия>[_<метка>].dump`, например `crm_2026-10-14_17-30-05_051f464….dump`:

- дата и время — когда снят бэкап, по Москве;
- версия — коммит приложения, которое работало в момент бэкапа; для бэкапа перед выкаткой — версия **до** этой выкатки, то есть версия, с которой эти данные жили; `none` — бэкап перед самой первой выкаткой;
- метки нет — бэкап перед выкаткой;
- `_daily` — ежедневный бэкап;
- `_before-restore` — копия базы, которую скрипт восстановления снял перед тем, как её заменить.

> Бэкапы лежат только на этом же сервере: если пропадёт сервер, пропадут и они.

Посмотреть бэкапы:

```bash
ssh crm
sudo ls -l /srv/personal-crm/backups
```

Восстановить базу прода запускаете вы, на сервере:

```bash
ssh crm
sudo -u deploy /srv/personal-crm/restore.sh /srv/personal-crm/backups/<имя файла>
```

Что делает скрипт:

1. Проверяет, что файл — действительно бэкап. До подтверждения ничего не меняет.
2. Показывает, какой файл загрузит, какую базу заменит, какая версия приложения работает и с какой версией снят бэкап. Ждёт, пока вы введёте `yes`; любой другой ответ — выход без изменений.
3. Снимает копию текущей базы (файл с `_before-restore`).
4. Останавливает приложение, удаляет базу, создаёт пустую и загружает в неё бэкап.
5. Запускает ту же версию приложения и ждёт, пока `/health` ответит. Версию приложения скрипт не меняет и миграции не запускает.

Бэкап нужно загружать в ту версию приложения, с которой он снят (версия в имени файла). Если версии отличаются, скрипт предупредит. Типичный случай — выкатка испортила данные:

1. Откатить прод на предыдущую версию (см. «Как откатить прод»).
2. Восстановить бэкап, снятый этой выкаткой: самый новый файл, в имени которого версия, на которую откатились (она в итогах запуска отката).

Если скрипт упал, он напишет, где лежит копия базы до восстановления; приложение может остаться остановленным. Сам он ничего не откатывает. Посмотреть логи: `sudo -u deploy /srv/personal-crm/compose.sh logs --tail 100 app db`. Вернуть базу как было — запустить `restore.sh` с этой копией.

### Что где лежит

- `Dockerfile` — образ приложения; в нём же скрипт миграций.
- `.github/workflows/ci.yml` — проверки каждого PR в `main`.
- `.github/workflows/deploy-staging.yml` (**Deploy staging**) — после влития в `main`: сборка образа и выкатка на стенд через `deploy/ship.sh`.
- `.github/workflows/deploy-prod.yml` (**Deploy prod**) — выкатка на прод и откат, только кнопкой: выбор версии (`deploy/prod-version.sh`), выкатка (`deploy/ship.sh` из выбранного коммита), итоги запуска (`deploy/prod-summary.sh`), чистка GHCR (`deploy/ghcr-cleanup.sh`).
- `deploy/` — всё для сервера: `environments.sh` (адрес, порт и папка каждого окружения), `compose.yaml` (приложение и база, один файл на оба окружения), `deploy.sh` (выкатка, окружение — первым параметром), `backup.sh` (бэкап базы прода и хранение по 7), `daily-backup.sh` (ежедневный бэкап), `restore.sh` (восстановление), `compose.sh`, `.env.example`, настройки nginx (`nginx/`) и таймера бэкапа (`systemd/`). Скрипты, которые работают на машине GitHub, а не на сервере: `ship.sh`, `ssh.sh`, `prod-version.sh`, `prod-summary.sh`, `ghcr-cleanup.sh`. Выкатка копирует на сервер всю папку: новый скрипт попадёт туда сам.
- На сервере — папки пользователя `deploy` (без sudo, заходит только CI по своим ключам): `/srv/personal-crm` у прода и `/srv/personal-crm-staging` у стенда. В каждой:
  - всё из `deploy/` — копирует каждая выкатка этого окружения, руками не править;
  - `.env` — пароль базы, секрет входа, ключ Resend (внутри `SMTP_URL`) и почта владельца, права 600, создаётся один раз руками по `deploy/.env.example`;
  - `release.env` — текущий и предыдущий образ;
  - `deploy.lock` — замок, чтобы на окружение шла одна выкатка, восстановление или бэкап за раз;
  - `backups/` — бэкапы базы, только у прода, читает только пользователь `deploy`.
- Таймер ежедневного бэкапа — `/etc/systemd/system/personal-crm-backup.timer` и `.service`, копии файлов из `deploy/systemd/`.
- У каждого окружения в Docker свой проект (`prod`, `staging`), своя база и свой том с данными. Лимиты памяти: приложение — 512 МБ, база — 256 МБ, контейнер миграций — 256 МБ.
- Настройки nginx `deploy/nginx/app.vprodcrm.ru.conf` и `deploy/nginx/test-app.vprodcrm.ru.conf` выкаткой не применяются (копия лежит в папке окружения, nginx её не читает): если поменяли — поставить на сервер руками. Пароль стенда — в `/etc/nginx/test-app.vprodcrm.ru.htpasswd`.
- В GitHub два окружения, оба доступны только ветке `main`: `staging` (его выкатывает Deploy staging) и `production` (Deploy prod). В каждом свой секрет `DEPLOY_SSH_KEY` — ключ деплоя — и переменные `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS`. История выкаток стенда в окружении `staging` — то, по чему Deploy prod проверяет, что версия прошла стенд.
- Логи контейнеров ограничены: до 3 файлов по 10 МБ на контейнер.

### Тестовые данные на сервере

База на сервере один раз заполнена тестовыми данными: 1000 контактов с заметками. Повторить можно только на пустой базе (иначе скрипт ничего не делает):

```bash
git archive HEAD | ssh crm "sudo -u deploy docker run -i --rm --network prod_default --env-file /srv/personal-crm/.env -e COREPACK_ENABLE_DOWNLOAD_PROMPT=0 node:24-alpine sh -euc 'mkdir /src && cd /src && tar -x && corepack enable && pnpm install --frozen-lockfile --reporter=silent && DATABASE_URL=\"postgres://crm:\${POSTGRES_PASSWORD}@db:5432/crm\" pnpm db:seed'"
```
