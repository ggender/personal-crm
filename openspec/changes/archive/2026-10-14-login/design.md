# Design

## Context

Зачем фича — в `proposal.md`, требования — в `specs/user-auth/spec.md`, `specs/data-ownership/spec.md` и `specs/contact-groups/spec.md`.

Как устроено сейчас:

- Пользователей нет. Все запросы к базе — в `src/lib/contacts.ts` и `src/lib/groups.ts` (только сервер), изменения — серверные действия в `src/app/actions.ts`. Ни одна функция не знает, чьи данные она читает.
- Шапка в `src/app/layout.tsx` — только логотип. Страницы: главная, карточка, «Изменить», «Новый контакт», «Группы». Название контакта попадает и в заголовок вкладки (`generateMetadata` карточки).
- Миграции применяет `scripts/migrate.ts`: локально `pnpm db:migrate`, на сервере — разовый контейнер до старта нового образа (`deploy/compose.yaml`, `deploy/deploy.sh`). Мигратор Drizzle применяет все новые миграции одной транзакцией: упала одна — не применилось ничего.
- Vitest работает на базе `crm_test`, Playwright — на `crm_e2e_test` и собранном приложении на порту 3100. В Vitest `next/server` и `server-only` подменены заглушками (`vitest.config.mts`). Помощники e2e кладут данные прямо в базу.
- CI: lint, формат, типы, Vitest и Playwright — каждый со своим Postgres в `services`, сборка образа.
- Next.js 16: `middleware` переименован в `proxy` (`src/proxy.ts`), работает на Node.js. Документация Next.js советует в proxy только быструю проверку по cookie, без запросов к базе, а настоящую проверку — на страницах и в действиях.

Что выяснилось о Better Auth 1.7.7 (последняя стабильная на сегодня, проверено по исходникам пакета):

- Плагин magic link: ссылка сгорает атомарно при первом открытии; срок задаётся `expiresIn` (по умолчанию 5 минут); любая негодная ссылка уводит на `errorCallbackURL` с `?error=INVALID_TOKEN`; почту сам приводит к маленьким буквам, но пробелы не убирает; отменять прежние ссылки и считать письма на почту не умеет.
- Встроенное ограничение запросов по IP в production включено по умолчанию.
- Хуки `hooks.before` выполняются и для HTTP-запросов, и для вызовов `auth.api.*` с сервера — одно место для проверок.
- Серверный компонент (RSC) не может ставить cookie. Если сессию продлевает RSC, срок в базе сдвигается, а cookie в браузере — нет.

## Goals / Non-Goals

**Goals:**

- Забыть про владельца нельзя: каждая функция работы с данными принимает `userId` первым параметром, TypeScript не даст вызвать её без него.
- Одна сборка везде: всё, чем компьютер, автотесты и сервер отличаются, — переменные окружения.
- Миграция безопасна: без почты владельца она останавливается целиком, база остаётся как была, новый образ не стартует.
- Вход проверяется настоящими письмами в настоящей заглушке, без моков в e2e.

**Non-Goals:**

- Row Level Security в Postgres: защита в коде плюс тесты на каждую функцию проще и достаточна для приложения такого размера.
- Клиентская библиотека Better Auth (`better-auth/react`): формы работают через серверные действия.
- Ограничение по IP — решение владельца.
- Шаблонизатор писем (react-email и т. п.) — новая библиотека; письмо собирается простой строкой HTML.

## Decisions

### 1. Better Auth: `src/lib/auth.ts`

- `getAuth()` создаёт объект Better Auth при первом вызове, как `getDb()` создаёт пул. Причина: `next build` в Docker загружает модули без секретов, и создание на уровне модуля уронило бы сборку образа.
- Настройки: адаптер Drizzle (`provider: "pg"`, `usePlural: true` — таблицы `users`, `sessions`, `accounts`, `verifications`; таблицы передаются из `src/db/schema.ts`), `advanced.database.generateId: "uuid"`, `session.expiresIn` — 30 дней, `session.updateAge` — 1 сутки, `rateLimit.enabled: false`. Вход по паролю не включён.
- Плагины: `magicLink({ expiresIn: 15 * 60, storeToken: { type: "custom-hasher", hash: sha256 }, sendMagicLink })` и последним `nextCookies()` — он ставит cookie из серверных действий.
- Секрет и адрес — из `BETTER_AUTH_SECRET` и `BETTER_AUTH_URL`.
- Обработчик: `src/app/api/auth/[...all]/route.ts`, `GET` и `POST` передают запрос в `getAuth().handler`.
- Свой хешер ссылок вместо встроенного `"hashed"`: в базе лежит только отпечаток ссылки, а мы можем посчитать отпечаток текущей ссылки сами и отменить все остальные (п. 7).
- Почему Better Auth, а не своё — так решил владелец; своё решение — больше кода в самом опасном месте.

### 2. Модель данных

```
users          — Better Auth: id uuid PK default gen_random_uuid(), name text not null (''),
                 email text not null unique, email_verified boolean, image text,
                 created_at, updated_at
sessions       — Better Auth: id, token unique, user_id → users (on delete cascade),
                 expires_at, ip_address, user_agent, created_at, updated_at
accounts       — Better Auth (нужна его ядру; при входе по ссылке пустая)
verifications  — Better Auth: id, identifier, value, expires_at, created_at, updated_at;
                 ссылки из писем: identifier = 'magic-link:' || sha256(ссылки)
login_emails   — наша: id identity PK, email text not null, sent_at timestamptz default now(),
                 index (email, sent_at) — учёт писем для лимита

contacts       + user_id uuid not null → users (on delete restrict)
                 index contacts_name_idx на (name collate "ru-x-icu") заменяется
                 на contacts_user_id_name_idx (user_id, name collate "ru-x-icu")
groups         + user_id uuid not null → users (on delete restrict)
                 unique groups_name_lower_idx (lower(name)) заменяется
                 на unique groups_user_id_name_lower_idx (user_id, lower(name))
notes, group_members — без изменений: заметка принадлежит владельцу контакта,
                 связь группы с контактом — их общему владельцу
```

- Схема таблиц Better Auth генерируется его CLI под эти настройки (версию CLI проверить при установке) и кладётся в `src/db/schema.ts`; миграцию по ней собирает `pnpm db:generate`, как раньше.
- `on delete restrict`: пользователя нельзя удалить из базы, пока у него есть контакты и группы, — случайное удаление строки не унесёт все данные. Удаления аккаунта в приложении нет.
- Почему без `user_id` у заметок и связей групп: владелец однозначно выводится из контакта и группы; лишняя колонка — лишний способ рассинхронизироваться. Что контакт и группа в одной связи принадлежат одному пользователю, проверяет код (п. 4) и тесты. Альтернатива — `user_id` в `group_members` и составные внешние ключи: защита на уровне базы, но сложнее миграция; отложено.
- Номера контактов и групп остаются числами: угадывание номера ничего не даёт, проверка владельца — в каждом запросе.

### 3. Миграции: `0003_auth.sql` и `0004_data_owner.sql`

Две миграции, чтобы та, что меняет существующие данные, была отдельной и короткой — её легко прочитать до merge. В выкатке обе применяются вместе, одной транзакцией.

`drizzle/0003_auth.sql` — `pnpm db:generate --name auth`: только `CREATE TABLE` для `users`, `sessions`, `accounts`, `verifications`, `login_emails`. Существующие таблицы не трогает.

`drizzle/0004_data_owner.sql` — **меняет существующие данные**. Создаётся `pnpm db:generate --name data_owner`, затем дописывается руками: Drizzle сгенерирует `ADD COLUMN user_id ... NOT NULL`, а на заполненной базе так нельзя. Порядок в файле:

1. `ALTER TABLE contacts/groups ADD COLUMN user_id uuid` — пока без `NOT NULL`.
2. Блок `DO $$ … $$`: если в `contacts` или `groups` есть хоть одна строка —
   - берёт почту владельца из `current_setting('app.owner_email', true)`, убирает пробелы, приводит к маленьким буквам;
   - пусто или не похоже на почту → `RAISE EXCEPTION 'OWNER_EMAIL is not set: existing contacts and groups need an owner'`; вся миграция откатывается;
   - создаёт пользователя с этой почтой (`name = ''`, `email_verified = false` — подтвердится первым входом) и проставляет его `user_id` всем контактам и группам.
   Если данных нет — пользователь не создаётся: владелец появится при первом входе, как любой другой.
3. `ALTER COLUMN user_id SET NOT NULL`, внешние ключи, новые индексы вместо старых.

Как почта попадает в SQL: `scripts/migrate.ts` читает `OWNER_EMAIL` и на своём единственном соединении выполняет `select set_config('app.owner_email', $1, false)` перед `migrate()`. В репозитории почты нет. Отвергнуто: почта в тексте миграции (репозиторий открытый); отдельный скрипт после миграций (тогда `NOT NULL` пришлось бы ставить следующей выкаткой).

Тестовые базы: `tests/prepare-test-database.mts` передаёт ту же настройку с почтой `owner@example.test`, потому что в `crm_test` и `crm_e2e_test` могут остаться строки от прошлых прогонов. В CI базы всегда пустые.

Что с данными:

- Контакты и группы получают владельца; заметки, частота, отметки «Пообщались», связи с группами не меняются; ни одна строка не удаляется. Число контактов, заметок, групп и связей до и после совпадает — это проверяет тест миграции (п. 12).
- На сервере это 1000 тестовых контактов; локально — то, что лежит в вашей базе.

Откат — только вместе, вручную, запускает владелец:

1. Прошлый образ: `deploy.sh <PREVIOUS_IMAGE>`. Он снимет ещё один бэкап — уже новой базы.
2. Бэкап, снятый этой выкаткой, через `restore.sh`: самый новый файл, в имени которого версия из `PREVIOUS_IMAGE`.

Прошлая версия с новой базой не работает: она добавляет контакты без `user_id`, а колонка обязательная. Миграции «вниз» нет. При восстановлении пропадает всё, что внесли после выкатки, в том числе пользователи друзей. В README — отдельный абзац про откат этой выкатки.

### 4. Владелец в каждой функции данных

- Все функции `src/lib/contacts.ts` и `src/lib/groups.ts` получают `userId: string` первым параметром и добавляют `user_id = $userId` в каждый запрос: `listContacts`, `countContacts`, `getContact`, `listNotes`, `countNotes`, `getContactTouchStatus`, `listOverdueContacts`, `createContact` (ставит владельца), `addNote`, `updateContact`, `deleteContact`, `setContactFrequency`, `markContacted`, `undoContacted`, `updateNote`, `listGroups`, `getContactGroupIds`, `createGroup`, `renameGroup`, `deleteGroup`, `setContactGroup`, `addContactToNewGroup`.
- Заметки — через контакт: изменение заметки проверяет, что её контакт принадлежит пользователю.
- `setContactGroup` в одной транзакции проверяет, что и контакт, и группа — этого пользователя; иначе `contact-not-found` / `group-not-found`. `addContactToNewGroup` ищет и создаёт группу только среди групп пользователя; конфликт `on conflict` — по новому индексу `(user_id, lower(name))`.
- Метки групп в списке (`array(...)` по `group_members`) верны сами: в связях только группы владельца контакта.
- Чужая запись отвечает так же, как несуществующая: те же «Контакт не найден», «Заметка не найдена», «Группа не найдена», страница `not-found` карточки. По ответу не понять, есть ли запись у другого.
- `resolveGroupFilter` получает только свои группы, поэтому чужая группа в адресе уже сейчас превращается в «Все» — как удалённая.

### 5. Кто вошёл: `src/lib/current-user.ts`

- `getCurrentUser()` — `cache()` от React вокруг `getAuth().api.getSession({ headers: await headers(), query: { disableRefresh: true } })`; возвращает `{ id, email }` или `null`.
- `disableRefresh` — потому что страницы рисует RSC, а он не может обновить cookie: срок продлевает отдельный запрос (п. 6).
- `requireUser()` для страниц: нет входа → `redirect("/login")`. Его вызывают все страницы приложения и `generateMetadata` карточки и «Изменить» (иначе имя чужого контакта попало бы в заголовок вкладки).
- Для действий — `userForAction()`: нет входа → `redirect("/login")`; база не ответила → действие возвращает «Не удалось сохранить. Попробуйте ещё раз.» (или своё сообщение об ошибке, как сейчас) и пишет в лог. Так сценарии «база недоступна» остаются верными.
- `src/proxy.ts` — быстрая проверка без базы: нет cookie сессии (`getSessionCookie` из `better-auth/cookies`) → редирект на `/login`. Не трогает `/login`, `/login/expired`, `/api/auth/*`, `/health`, `/_next/*` и иконки. Это не защита, а быстрый путь: защита — в `requireUser()` и в `userId` каждой функции. Устаревшая cookie пройдёт proxy, но страница всё равно отправит на вход.
- В Vitest `@/lib/current-user` подменяется заглушкой `tests/shims/current-user.ts` (`signInAs(userId)`), как уже подменён `next/server`. Настоящий модуль проверяют e2e.

### 6. Срок входа, несколько устройств, выход

- Cookie сессии постоянная (с `Max-Age` 30 дней), поэтому переживает закрытие браузера. Каждый вход — своя строка в `sessions`: устройства не мешают друг другу.
- Продление: клиентский компонент `SessionRefresh` в шапке при каждой загрузке страницы делает `fetch("/api/auth/get-session")`. Это обработчик маршрута, он может поставить cookie: если с прошлого продления прошли сутки, Better Auth сдвигает срок и в базе, и в cookie на 30 дней вперёд. Отсюда «30 дней с точностью до суток». Альтернатива — продлевать в `proxy.ts` с запросом к базе на каждую загрузку — Next.js так делать не советует.
- Выход — форма с серверным действием `signOutAction`: `getAuth().api.signOut({ headers })` удаляет только сессию этого устройства, `nextCookies()` стирает cookie, затем `redirect("/login")`. Работает и без JavaScript.
- Шапка: `layout.tsx` вызывает `getCurrentUser()`; есть пользователь — справа почта (`truncate`) и «Выйти», иначе только логотип. Цвета и отступы — токены из `src/styles/tokens.css`.

### 7. Запрос ссылки

```
форма /login ──► requestLoginLinkAction ──► auth.api.signInMagicLink ──┐
прямой POST /api/auth/sign-in/magic-link ──────────────────────────────┤
                                                                       ▼
           hooks.before (/sign-in/magic-link): почта → trim → lower → проверка
                     неверная → 400 INVALID_EMAIL, дальше не идём
                                                                       ▼
           Better Auth создаёт ссылку (в базе — отпечаток, срок 15 минут)
                                                                       ▼
           sendMagicLink (транзакция, pg_advisory_xact_lock по почте):
             писем за 10 минут ≥ 3 → удалить только что созданную ссылку,
                                     429 LOGIN_EMAIL_LIMIT
             отправить письмо (сбой → ошибка, прежние ссылки целы)
             удалить прочие ссылки этой почты (отпечаток ≠ текущему)
             записать письмо в login_emails, стереть записи старше суток
```

- Почта проверяется в одном месте — хуке, поэтому форма и запрос в обход формы ведут себя одинаково. Правило — `loginEmailSchema` в `src/lib/validation.ts`: обрезка пробелов, маленькие буквы, `z.email()`, не длиннее 254 символов.
- Лимит, отмена прежних ссылок и учёт — `src/lib/login-emails.ts`. Блокировка по почте делает «посчитать — отправить — записать» неделимым: два одновременных запроса не отправят четвёртое письмо. В лимит попадают только ушедшие письма; отказ по лимиту и сбой отправки прежние ссылки не трогают.
- Страница `/login` (серверная): вошедшего отправляет на `/`. Форма `LoginForm` — `useActionState`, `noValidate`, поле `type="email"` с `autocomplete="email"`. После успеха форма остаётся с почтой, под кнопкой `role="status"` — «Ссылка для входа отправлена на <почта>» (почта уже приведена к виду, в котором её сохранили). Ошибки: `INVALID_EMAIL` → «Проверьте адрес почты» под полем; `LOGIN_EMAIL_LIMIT` → «Слишком часто, попробуйте через несколько минут»; остальное → «Не удалось отправить письмо. Попробуйте ещё раз.» и запись в лог на английском.
- `callbackURL` и `newUserCallbackURL` — `/`, `errorCallbackURL` — `/login/expired`. Better Auth сам проверяет, что эти адреса ведут на наш сайт.

### 8. Ссылка и страница «Ссылка устарела»

- Ссылка ведёт на `/api/auth/magic-link/verify?token=…`. Better Auth сжигает её, при первом входе создаёт пользователя (`name = ''`), создаёт сессию, ставит cookie и отправляет на `/`.
- Любая ошибка — использованная, просроченная, отменённая, испорченная ссылка — `/login/expired?error=…`. Страница: «Ссылка устарела, запросите новую» и кнопка-ссылка «На страницу входа» (`/login`). Код ошибки только пишется в лог.

### 9. Письмо: `src/lib/mail.ts`

- Nodemailer: `createTransport(process.env.SMTP_URL)` — один раз, лениво. Отправитель — `MAIL_FROM`. На компьютере и в CI `SMTP_URL=smtp://127.0.0.1:1025` (Mailpit), на сервере `smtps://resend:<ключ>@smtp.resend.com:465`. Нет переменной — понятная ошибка при отправке.
- Письмо: тема «Вход в Личную CRM»; HTML с кнопкой «Войти», «Ссылка работает 15 минут.», «Если вы не запрашивали вход - просто проигнорируйте письмо»; та же информация простым текстом со ссылкой. Почтовые программы не понимают CSS-переменные, поэтому цвета письма — значения из `tokens.css`, собранные в одном месте рядом с шаблоном.
- Resend по SMTP: если хостер закрыл порт 465, у Resend есть 2465 (и 587/2587 со STARTTLS) — меняется только `SMTP_URL`.

### 10. Настройки

| Переменная           | Компьютер (`.env`)                       | Автотесты и CI                         | Сервер                                 |
| -------------------- | ---------------------------------------- | -------------------------------------- | -------------------------------------- |
| `BETTER_AUTH_SECRET` | случайный, создаёт `pnpm env:init`       | одноразовый, в `playwright.config.ts`  | `.env`, секрет                         |
| `BETTER_AUTH_URL`    | `http://localhost:3000`                  | `http://127.0.0.1:3100`                | `deploy/compose.yaml`                  |
| `SMTP_URL`           | `smtp://127.0.0.1:1025`                  | `smtp://127.0.0.1:1025`                | `.env`, в нём ключ Resend              |
| `MAIL_FROM`          | `Личная CRM <noreply@mail.crm.vprodcrm.ru>`  | то же, в `playwright.config.ts`        | `deploy/compose.yaml`                  |
| `OWNER_EMAIL`        | ваша почта                               | `owner@example.test` (только миграция) | `.env`; нужна миграции и `db:seed`     |

- `pnpm env:init` научится дописывать недостающие строки в уже существующий `.env`, не меняя имеющихся и не печатая значений; `OWNER_EMAIL` оставит пустой и попросит вписать почту. Запускаете вы: агент `.env` не читает и не пишет.
- `deploy/compose.yaml`: сервису `app` — `BETTER_AUTH_SECRET` и `SMTP_URL` из `.env` (обязательные, `:?`), `BETTER_AUTH_URL=https://app.vprodcrm.ru`, `MAIL_FROM`; сервису `migrate` — ещё `OWNER_EMAIL` (обязательная). Не задана — compose падает на первой же команде `deploy.sh`, ещё до бэкапа и миграций.
- Локально `pnpm dev` открывать по адресу из README — http://localhost:3000: на него настроен `BETTER_AUTH_URL`, с другого адреса Better Auth отклонит запрос.

### 11. Mailpit

- `docker-compose.yml`: сервис `mailpit` (`axllent/mailpit`, последняя версия на момент реализации), порты `127.0.0.1:1025` (SMTP) и `127.0.0.1:8025` (страница), проверка готовности. `pnpm db:up` поднимает базу и Mailpit вместе. Письма хранятся в памяти и пропадают при перезапуске — это заглушка.
- CI: в задаче Playwright — сервис `mailpit` с теми же портами.
- Помощник e2e `e2e/helpers/mailpit.ts` ищет письма через API Mailpit по адресу получателя (`/api/v1/search?query=to:"…"`) и достаёт ссылку из письма. Каждый тест пишет на свой одноразовый адрес, поэтому тесты не трогают чужие письма и не упираются в лимит.

### 12. Тесты

Один тест на сценарий, название теста = название сценария, `describe` = название требования.

- Vitest:
  - `tests/data-ownership.test.ts` — функции данных и серверные действия от имени B с номерами записей A: что вернули и что осталось у A. Сюда же «Чужое не меняется запросом к серверу».
  - `tests/data-owner-migration.test.ts` — отдельная база `crm_migration_test`: применить миграции до `0002` (копия папки `drizzle/` с укороченным журналом), положить контакты, заметки, группы и связи, применить остальные с почтой владельца → владелец создан, всем записям проставлен, числа совпадают; с данными и без почты → ошибка, база не изменилась; пустая база без почты → проходит, пользователей нет.
  - `tests/seed.test.ts` — `pnpm db:seed` на пустой тестовой базе с `OWNER_EMAIL`: 1000 контактов у владельца, у другого пользователя пусто.
  - `tests/user-auth.test.ts` — правило почты; «Почтовый сервис недоступен»: настоящее действие и настоящий Better Auth на тестовой базе, `SMTP_URL` указывает на закрытый порт (как `db-down`-тесты).
  - Существующие тесты: помощники `makeContact`, `makeGroup` получают владельца, функции — `userId`, действия идут от имени тестового пользователя. Проверки не ослабляются.
- Playwright:
  - `e2e/user-auth.spec.ts` — все сценарии входа, кроме «Почтовый сервис недоступен». Время не ждём, а сдвигаем в базе: срок ссылки (`verifications.expires_at`), даты писем (`login_emails.sent_at`), срок и дату продления сессии (`sessions.expires_at`, `updated_at`). «В обход формы» — прямой `POST /api/auth/sign-in/magic-link`.
  - `e2e/data-ownership.spec.ts` — A и B в двух браузерах: критерий успеха из спеки и остальные сценарии `data-ownership`, которые видны на экране.
  - `main-scenario.spec.ts` и `keep-in-touch.spec.ts` перед сценарием входят; «другой браузер» в главном сценарии входит под той же почтой.
- Руками не проверить (только автотестом): «Неверный адрес в обход формы», «Попытка изменить чужие записи», «Своя группа и чужой контакт», «Не заходил больше 30 дней», «Заход продлевает срок». Настоящая доставка через Resend — только руками после выкатки: автотесты настоящих писем не шлют.

## Risks / Trade-offs

- [Опечатка в `OWNER_EMAIL` на сервере — данные уйдут пользователю с чужим адресом] → До merge вы сверяете строку сами; после выкатки входите и видите «1000 контактов». Ошиблись — поправить почту одной командой SQL на сервере (её дам) или откат.
- [Resend не подтвердил домен или хостер закрыл порт — на сервере никто, включая вас, не войдёт] → До merge: домен в Resend «Verified», с сервера проверяем доступность порта SMTP Resend. Если после выкатки письма не уходят — откат по п. 3.
- [Письма попадают в «Спам»] → Записи SPF и DKIM от Resend для `mail.crm.vprodcrm.ru`; запись DMARC — по желанию.
- [Кто-то просит ссылки на сотни адресов и исчерпывает дневной лимит Resend] → Принято владельцем; при необходимости — ограничение по IP отдельной правкой.
- [Несколько секунд между миграцией и стартом нового образа старая версия не сможет сохранить новый контакт] → Окно — секунды, пользователь один; повторное нажатие после старта сработает.
- [Откат стирает всё, что внесли после выкатки] → Предупреждение в README; откатывать, только если выкатка сломала данные.
- [Связь контакта и группы разных пользователей из-за ошибки в коде] → Проверка в транзакции и тесты на каждый путь; ограничение на уровне базы отложено (п. 2).
- [Заглушка `current-user` в Vitest прячет настоящую проверку входа] → Настоящую проверяют e2e на каждом сценарии.
- [Ссылку из письма откроют в почтовом клиенте, который заранее «проверяет» ссылки и сжигает их] → Известное свойство одноразовых ссылок; лечится только кнопкой подтверждения на странице, в спеке её нет.
- [Обновление Better Auth поменяет поведение] → Версия закреплена в `pnpm-lock.yaml`; тесты входа поймают изменения.

## Migration Plan

1. До merge, руками — вы:
   - аккаунт Resend, домен `mail.crm.vprodcrm.ru`, записи DNS из Resend на reg.ru, статус «Verified», ключ API с правом отправки;
   - в `/srv/personal-crm/.env` на сервере: `BETTER_AUTH_SECRET` (команда сгенерирует, не показывая), `SMTP_URL` с ключом, `OWNER_EMAIL`; права 600 остаются.
2. До merge — агент: проверяет без вывода значений, что строки есть (`grep -c`), что с сервера открывается порт SMTP Resend; показывает вам текст миграции `0004_data_owner.sql`.
3. Merge → выкатка как обычно: бэкап (версия до выкатки в имени файла) → образ → миграция в разовом контейнере (владелец данным) → новое приложение → smoke `/health`.
4. После выкатки — вы: без входа app.vprodcrm.ru показывает страницу входа; вход по своей почте — письмо пришло, внутри «1000 контактов»; вход с другой почтой — пусто; «Выйти» работает.
5. Откат — п. 3, только вручную.
