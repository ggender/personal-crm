# Design

## Context

Зачем фича — в `proposal.md`, требования — в `specs/contact-groups/spec.md`.

Как устроено сейчас:

- В базе две таблицы: `contacts` и `notes`. Все запросы к базе — в `src/lib/contacts.ts` (только сервер), изменения — через серверные действия в `src/app/actions.ts`.
- Главная `src/app/page.tsx` читает `?q=` из адреса, рисует шапку (заголовок, число контактов, поиск `ContactSearch`), блок «Пора связаться» и список по буквам. Строка списка — `ContactListLink`.
- На странице контакта `src/app/contacts/[id]/page.tsx` — список полей `<dl>`; в нём строка «Как часто общаться» с `ContactFrequencyPicker`: нативные радиокнопки в виде «таблеток», сохранение сразу, `useOptimistic` откатывает выбор при ошибке.
- Есть `ConfirmDelete` — диалог подтверждения удаления.
- Автотестов в репозитории нет. Vitest и Playwright записаны в стеке, но не подключены.
- Функции чтения в `src/lib/contacts.ts` вызывают `connection()` из `next/server`; вне запроса Next.js (в тестах) он бросает ошибку. `revalidatePath` вне запроса тоже бросает ошибку.

## Goals / Non-Goals

**Goals:**

- Фильтр и метки — одним запросом к базе на страницу, без отдельного запроса на каждого человека.
- Фильтр работает обычными ссылками: с историей браузера, адресом и до загрузки JavaScript.
- Повторить уже знакомые в приложении приёмы: «таблетки» как у частоты, `ConfirmDelete`, формы на `useActionState`.
- Подключить Vitest на настоящей базе так, чтобы следующие фичи просто добавляли тесты.

**Non-Goals:**

- Playwright, браузерные тесты и прогон тестов в CI — отдельно, позже.
- Тесты компонентов в эмуляции браузера (jsdom и Testing Library — новые библиотеки).
- Переделка «Пора связаться», поиска и форм контакта сверх того, что нужно для фильтра.

## Decisions

### 1. Модель данных: таблица групп и таблица связей

```
groups
  id          integer, identity, PK
  name        text not null, check (char_length(name) between 1 and 50)
  created_at  timestamptz not null default now()
  unique index groups_name_lower_idx on (lower(name))

group_members
  group_id    integer not null → groups.id on delete cascade
  contact_id  integer not null → contacts.id on delete cascade
  created_at  timestamptz not null default now()
  primary key (group_id, contact_id)
  index group_members_contact_id_idx on (contact_id)
```

- Связь «многие ко многим»: человек в нескольких группах, в группе много людей. Первичный ключ из пары не даёт добавить человека в группу дважды.
- `on delete cascade` с двух сторон: удалил группу — пропали только её связи, люди остались; удалил контакт — он пропал из всех групп. Отдельного кода для этого не нужно.
- Уникальность без учёта регистра — индексом по `lower(name)`. `lower()` уже работает с кириллицей в нашей базе: на нём держится поиск по имени.
- Почему не массив id групп в `contacts` и не текстовые метки у контакта: у массива нет внешних ключей, и удаление группы пришлось бы чистить руками; текстовые метки при переименовании пришлось бы переписывать у всех людей, а «Теннис» и «теннис» стали бы разными группами.
- `groups` в Postgres — не зарезервированное слово, Drizzle всё равно берёт имена в кавычки.

### 2. Миграция `drizzle/0002_groups.sql`

- Создаётся командой `pnpm db:generate --name groups` из `src/db/schema.ts`. В ней только `CREATE TABLE` двух таблиц, внешние ключи и индексы; существующие таблицы она не трогает.
- Что с данными: контакты и заметки не меняются; после миграции групп нет, у всех контактов групп нет — ровно то, что требует спека («Сначала групп нет»).
- Выкатка обычная: миграция в разовом контейнере до старта нового образа.
- Откат: владелец вручную запускает предыдущий образ. Старый код про новые таблицы не знает и работает как раньше, таблицы можно оставить — при повторной выкатке группы вернутся. Убрать таблицы совсем — `drop table group_members; drop table groups;` и удалить строку миграции из `drizzle.__drizzle_migrations`; при этом группы теряются, поэтому только с согласия владельца.

### 3. Данные: `src/lib/groups.ts` и фильтр в `src/lib/contacts.ts`

Новый модуль `src/lib/groups.ts` (`server-only`):

- `listGroups()` → `{ id, name, contactCount }[]`, по алфавиту (`ru-x-icu`, как имена контактов), затем по `id`.
- `getContactGroupIds(contactId)` → `number[]` для страницы контакта.
- `createGroup(name)` → `{ id }` или `{ duplicateOf: <имя существующей> }`. Вставка `on conflict do nothing`, при конфликте — чтение существующей по `lower(name)`: так нет гонки «проверил — вставил».
- `addContactToNewGroup(contactId, name)` — одна транзакция: найти или создать группу без учёта регистра, добавить человека (`on conflict do nothing`). `null`, если контакта нет.
- `setContactGroup(contactId, groupId, member)` — добавить (`on conflict do nothing`) или убрать связь; повторное нажатие в другой вкладке ничего не ломает. Обновляет `contacts.updated_at`, как смена частоты. Возвращает `"ok" | "contact-not-found" | "group-not-found"`.
- `renameGroup(groupId, name)` → `"ok" | "not-found" | { duplicateOf }`. Нарушение уникальности (код `23505`) превращается в `duplicateOf`. Переименовать «теннис» в «Теннис» можно: индекс сравнивает с другими строками.
- `deleteGroup(groupId)` → `false`, если группы уже нет.

Фильтр — тип `GroupFilter = { kind: "all" } | { kind: "group"; groupId } | { kind: "none" }`:

- `listContacts(query, filter)` добавляет к условиям поиска `exists (… group_members … group_id = …)` или `not exists (…)` и возвращает у каждого человека `groups: string[]` — названия его групп по алфавиту, одним подзапросом с `array_agg`. На 1000 контактов это быстро благодаря индексу по `contact_id`.
- `countContacts(filter)` — число под заголовком «Контакты» с тем же фильтром.
- `listOverdueContacts()` не меняется: блок «Пора связаться» фильтр не учитывает.

### 4. Фильтр в адресе: `?group=12`, `?group=none`

- В адресе id группы, а не название: переименование не ломает сохранённые ссылки, в названии могут быть любые символы. `none` — «Без группы», с числами не путается. Вместе с поиском: `/?group=12&q=иван`.
- Чистые функции без сервера — в `src/lib/group-filter.ts`, чтобы их проверяли тесты:
  - `resolveGroupFilter(raw, groups)` — разбор параметра; неизвестный или удалённый id и мусор → «Все».
  - `groupFilterItems(groups, filter, query)` — кнопки фильтра по порядку («Все», группы, «Без группы»): подпись, адрес с сохранённым `q`, выбрана ли; плюс ссылка «Группы» на `/groups`. Пустой список групп → пустой результат: фильтра нет.
  - `contactsHref({ filter, query })` — общий сборщик адреса главной; им же пользуются поиск и ссылка «Искать во всех контактах».
  - `emptyListMessage(filter, groups, query)` — что написать вместо пустого списка и нужна ли ссылка «Искать во всех контактах» (тексты — в п. 5).
- Главная сначала читает `listGroups()`, затем по нему разбирает фильтр и уже с ним запрашивает список и число — лишнего запроса для проверки группы нет.

### 5. Главная

- `GroupFilter` — серверный компонент: `<nav aria-label="Фильтр по группам">` со ссылками `<Link>`, у выбранной `aria-current="page"` и вид выбранной «таблетки» частоты (`border-ink bg-ink text-bg`). Ряд не переносится, листается вбок (`overflow-x-auto`, на телефоне до краёв экрана). В конце — ссылка «Группы» со значком на `/groups`. Рисуется, только если групп больше нуля. Стоит в липкой шапке под поиском.
- `ContactSearch` получает текущий фильтр: адрес поиска собирается через `contactsHref`, а форма без JavaScript получает скрытое поле `group`.
- Подзаголовок: `plural(countContacts(filter))`; при поиске — «Найдено N из M», где M — то же число с фильтром.
- Пустые состояния: пустая группа — «В группе «…» пока никого нет»; «Без группы» пусто — «Все контакты разложены по группам»; поиск в группе пуст — «Никого не нашлось по запросу «…» в группе «…»» и ссылка «Искать во всех контактах» (`/?q=…`); без фильтра — как сейчас, с «Добавить «…»».
- Метки: в `ContactListLink` под строкой «Кто это» — список маленьких плашек (`rounded-full bg-strip text-13 text-muted`), в одну строку, лишнее обрезается. Подсказка высоты строки для `content-visibility` увеличивается под строку с метками. `KeepInTouchSection` не меняется — меток в блоке нет.

### 6. Страница контакта

- Строка «Группы» в `<dl>` перед «Как часто общаться». Данные — `listGroups()` и `getContactGroupIds(id)` в общем `Promise.all`.
- Клиентский компонент `ContactGroupsPicker`: нативные чекбоксы в виде «таблеток» с теми же классами, что у `ContactFrequencyPicker`; у отмеченной — значок галочки. `useOptimistic` над набором id и `useTransition`; при ошибке — сообщение под строкой (`aria-live`), а кнопка сама возвращается к значению с сервера. Тот же приём с «нажатием до загрузки страницы», что у частоты.
- «+ Новая группа» — кнопка, которая превращается в маленькую форму: поле (до 50 символов), «Добавить», «Отмена»; Enter сохраняет, Esc закрывает. Форма на `useActionState`, ошибки под полем. После успеха форма закрывается, страница обновляется, новая группа уже отмечена.
- Нет ни одной группы — в строке надпись «Групп пока нет» и кнопка «+ Новая группа».
- Под «таблетками» — ссылка «Настроить группы» на `/groups`.
- Группу, удалённую в другой вкладке, отметить нельзя: действие вернёт «Группа не найдена», а обновлённая страница её уже не покажет.

### 7. Страница «Группы» `src/app/groups/page.tsx`

- Серверная страница: «Все контакты» назад, заголовок «Группы», форма «Новая группа», список групп из `listGroups()`.
- Строка группы — клиентский `GroupRow`: название — ссылка на `/?group=id`, подпись «N контактов» через `plural`, кнопки-значки «Переименовать» (карандаш, с `aria-label`) и «Удалить» (корзина).
- «Переименовать» превращает название в форму с полем и «Сохранить» / «Отмена». Ошибки под полем.
- «Удалить» открывает `ConfirmDelete`: «Удалить группу «Теннис»?» и «Люди останутся в контактах, пропадёт только группа.» Действие возвращает `{}` — диалог закрывается, строка пропадает после обновления.
- Пустой список: «Групп пока нет» и подсказка создать первую.

### 8. Серверные действия в `src/app/actions.ts`

- `setContactGroupAction(contactId, groupId, member)` → `SaveResult`.
- `createGroupForContactAction(contactId, prev, formData)`, `createGroupAction(prev, formData)`, `renameGroupAction(groupId, prev, formData)` → `GroupFormState = { error?, name?, savedAt? }` — как у заметок: при ошибке введённое название возвращается в поле.
- `deleteGroupAction(groupId)` → `DeleteResult`; группы уже нет — тоже успех, как у удаления контакта.
- Проверка названия — `groupNameSchema` в `src/lib/validation.ts`: обрезка пробелов, «Укажите название», «Не длиннее 50 символов». Повтор — «Группа «<существующее название>» уже есть». Остальные ошибки — «Не удалось сохранить. Попробуйте ещё раз.» с записью в лог на английском.
- Обновление страниц: отметка группы у контакта — `revalidatePath("/")`, страница контакта и `/groups`; создание, переименование, удаление — `revalidatePath("/", "layout")`, потому что название группы видно на всех страницах.

### 9. Тесты: Vitest на настоящей базе

- `vitest` — dev-зависимость, последняя стабильная версия на момент установки (проверить `pnpm view vitest version`). Команды `pnpm test` и `pnpm test:watch`.
- `vitest.config.ts`: окружение `node`; алиас `@` → `src`; файлы по одному (`fileParallelism: false`), потому что база общая и тесты её очищают. Два алиаса только для тестов: `server-only` → его же пустой файл `empty.js` (так пакет ведёт себя на сервере Next.js), `next/server` → крошечная заглушка с `connection()`, которая сразу возвращает управление. Код приложения ради тестов не меняется.
- Отдельная база `crm_test` в том же Docker-контейнере. Конфиг читает `.env` через `@next/env` (он уже есть), берёт `DATABASE_URL` и меняет имя базы на `crm_test`; если задан `TEST_DATABASE_URL` (пригодится в CI), берёт его. Владельцу ничего дописывать в `.env` не нужно.
- `globalSetup`: создаёт `crm_test`, если её нет, и применяет миграции из `drizzle/` тем же мигратором Drizzle. Перед каждым тестом — `truncate … restart identity cascade`.
- Защита: тестовый помощник отказывается работать, если имя базы не кончается на `_test`, — рабочую `crm` и прод тесты не тронут.
- Сценарий → тест: один `it(...)` на каждый `#### Scenario`, с тем же названием, внутри `describe` с названием требования, в `tests/contact-groups.test.ts`. Тесты проверяют серверную часть: что сохранилось в базе, что вернут `listContacts`, `countContacts`, `listGroups`, что соберут функции фильтра и что ответят проверки названия.
- Сценарии «база недоступна» — в отдельном файле `tests/contact-groups.db-down.test.ts`: там `DATABASE_URL` указывает на закрытый порт, и вызывается само серверное действие. На ошибке оно возвращается до `revalidatePath`, поэтому работает вне Next.js. Сбой настоящий, без заглушек базы.
- Что тест сейчас не видит: подсветку кнопок, откат «таблетки» после ошибки, кнопку «Отмена» в диалоге, обрезку вставки полем до 50 символов. Для этих сценариев тест проверяет серверную половину, а экран — руками и позже Playwright.

## Risks / Trade-offs

- [Алиас `next/server` в тестах скрывает настоящий `connection()`] → Алиас только в `vitest.config.ts`; сборку и работу приложения он не затрагивает. Зачем он, написано рядом в комментарии.
- [Тесты очищают таблицы] → Работают только с базой, имя которой кончается на `_test`; иначе падают сразу, ничего не удалив.
- [Липкая шапка становится выше на строку фильтра — на телефоне меньше места под список] → Фильтр в одну строку с прокруткой вбок, без переноса.
- [Длинный ряд групп: выбранная может оказаться за краем экрана] → При открытии главной выбранная кнопка прокручивается в видимую часть ряда.
- [Метки в каждой строке списка — лишняя работа базы] → Один подзапрос с индексом по `contact_id`; на 1000 контактов это доли миллисекунды на строку.
- [Группу удалили в другой вкладке] → Отметка вернёт «Группа не найдена», фильтр по старой ссылке откроет «Все».
- [`revalidatePath("/", "layout")` обновляет все страницы] → Группы меняются редко, а у приложения один пользователь.
